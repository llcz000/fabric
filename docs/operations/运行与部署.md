# Fabric 运行与部署

> **现行运维入口**。实际发布命令统一使用[统一发布工具](统一发布工具.md)；过时的按日期脚本和旧控制器双目录不再适用。发布必须有用户明确授权，本文件不授予部署权限。

## 本地

从单根 `D:/fabric` 安装依赖并运行 `npm run dev`。实际生产/测试凭据在本机受保护配置和 `.env` 中，不能写入知识库。构建运行 `npm run lint`、`npm run build`，按需要运行 `npm run test:unit`、`npm run test:security` 或 UI 专项。当前 `server.ts` 只接受 V2 生产目标，配置不成立会拒绝启动，不再回退旧JSON/legacy应用。

## 线上进程与持久目录

| 用途 | 目录与进程 | 访问方式 |
| --- | --- | --- |
| 生产 | `/opt/fabric` · `fabric` · `start-v2.cjs` | Nginx HTTPS 转发至 `127.0.0.1:3008` |
| 只读恢复 | `/opt/fabric` · `fabric-readonly` · `start-recovery.cjs` | `127.0.0.1:3009`，启动后代理 3008 并限制写请求 |
| 发布暂存与回退 | `/opt/fabric-backups/releases/<ID>` 与 `/opt/fabric-backups/release-<ID>` | 冻结制品、数据库备份和阶段回执，最多保留一个可回退的程序版本 |
| 候选 | `/opt/fabric-candidate/<名称>` · 私有 PM2 daemon | `127.0.0.1:31xx`，单独的 MySQL schema、账号、COS 与上传目录 |

生产 PM2 配置由仓库 `scripts/release/ecosystem.config.cjs` 安装到 `/opt/fabric/ecosystem.config.cjs`。首次恢复启动先执行 `pm2 start /opt/fabric/ecosystem.config.cjs --only fabric`，验证 3008 后启动 `--only fabric-readonly`，再验证 3009 并执行 `pm2 save`。常规发版由发布器只重启 `fabric`。现有运行配置、`uploads/`、模板目录及模板配置保留在固定根目录。生产与只读日志位于 `/root/.pm2/logs/`，文件名可能带 PM2 进程编号。用 `pm2 describe fabric`、`pm2 describe fabric-readonly` 核对实际位置，用 `pm2 logs <进程名>` 查看。两个进程各为单实例 fork，退出后由 PM2 自动重启。只读进程重启延迟 1 秒，启动依赖 3008 健康。

Nginx 的 `/v2-camera/` 静态资源由 `/opt/fabric/camera/current/` 提供。相机保留线上版和它的上一版目录，回退包仅保留上一版，位于 `/opt/fabric-backups/camera/`。用 `rollback-release.txt` 指明上一版目录。每次相机发布验收后更新该记录，核对上一版可回切，再清理更老版本。回退静态相机时将 `current` 切到该静态目录内对应的版本，再核对公开首页和资源。证书续签由 `fabric-certbot-renew.timer` 调用 `/opt/fabric/ops/certbot/bin/certbot`，续签配置、证书和工作目录沿用 `/etc/letsencrypt-fabric`。专项历史归档存于 `/var/backups/fabric`。

### 候选环境

候选使用独立且可重建的制品。将其解包为 `/opt/fabric-candidate/<名称>` 下的专用目录并建立独立 `uploads/`。目录和 `.env` 仅允许运维账号访问。候选库名以 `fabric_candidate_` 或 `fabric_release_check_` 开头，数据库账号只对该库授权。准备独立的 COS 桶和仅能访问该桶的凭据。启动工具核对数据库连接、schema 授权、COS 配置与生产相异、回环端口和文件链接，COS 账号的桶范围由配置时的授权策略保证。

```sh
python3 /opt/fabric-candidate/candidate.py start <名称>
python3 /opt/fabric-candidate/candidate.py status <名称>
python3 /opt/fabric-candidate/candidate.py stop <名称>
python3 /opt/fabric-candidate/candidate.py clean <名称>
```

候选 PM2 状态与日志位于 `/opt/fabric-candidate/.state/pm2/`。候选无需追加公网路由，也无需纳入生产 PM2 的开机配置。`clean` 清理已停止候选的应用文件，独立 MySQL 和 COS 的销毁在其对应环境单独确认后执行。历史候选停止后归档证据，使用同一生产 COS 或 uploads 的原配置不可再启动。

## 首次安装或恢复到新服务器

日常发布以已验证的线上服务为起点。首次安装或主机恢复先重建已验证的基线，再交给统一发布器。

1. **准备版本。** 在 `D:/fabric` 的目标 Git 分支安装锁定依赖，核对 Git 提交及远端分支。主应用由 `npm run build` 输出 `dist/`，相机输出 `dist-camera/`。已有有效发布时优先使用对应的冻结制品和恢复备份。现行应用构建工作站使用 Node 24，生产运行验证使用 Node 22。部署主机准备 Node、npm、PM2、Python 3、MySQL 客户端、Nginx、OpenSSL 和 systemd。
2. **建立目录和数据。** 建立 `/opt/fabric`、权限 0700 的 `/opt/fabric-backups` 和 `/opt/fabric-candidate`。在生产根目录恢复已验证的 `dist/`、`uploads/`、模板及配置。按本次后端的锁文件在 Linux 安装运行依赖，例如 `npm ci --omit=dev`。后端制品外置 Node 依赖，需要验证 Linux 环境实际能加载，特别是原生 `sharp`。恢复原 MySQL 数据至预定数据库，验证物理实例标识和 schema。通过受控来源安装权限 0600 的运行配置与运维登录凭据，再核对独立 COS 访问和生产目录下两个启动脚本的 SHA256。
3. **安装启动文件。** 从 `scripts/release/host/` 将 `start-v2.cjs`、`start-recovery.cjs` 安装到 `/opt/fabric/`。同时安装 `scripts/release/ecosystem.config.cjs` 至生产根目录，并安装 `scripts/release/candidate.py` 至候选根目录。恢复只读使用的 `dist/recovery.cjs` 通过当前源码专门构建或从已验证的备份恢复。
4. **安装 HTTPS 和相机入口。** 从 `scripts/release/host/` 安装 `fabric-site.conf` 至 `/etc/nginx/sites-available/fabric`，通过 `sites-enabled/fabric` 启用，并将 `fabric-v2-camera.conf` 安装到 `/etc/nginx/snippets/fabric-v2-camera.conf`。同时恢复单独验证过的相机制品和相对链接 `/opt/fabric/camera/current`。
5. **恢复证书续签。** 用 Python venv 在 `/opt/fabric/ops/certbot` 安装 `scripts/release/host/certbot-requirements.txt` 锁定的依赖。从受控备份恢复 `/etc/letsencrypt-fabric`，恢复 ACME Webroot `/var/lib/fabric-acme`。如需首次签发，先只启用 80 端口的 ACME Webroot 路由，使用 Certbot 的 `certonly --webroot -w /var/lib/fabric-acme --ip-address <公网IP> --preferred-profile shortlived --cert-name fabric-ip` 和指定的配置、工作、日志目录完成签发，再启用 TLS 站点。将 `reload-nginx-after-certbot.sh` 安装在 `/opt/fabric/ops/`，并由续签的 deploy-hook 目录软链接引用。安装并启用仓库中的续签 service 与 timer，执行 `nginx -t` 后再加载配置，并用 Certbot 的 `renew --dry-run --run-deploy-hooks` 核对完整续签链路。
6. **启动与验收。** 先启动 `fabric` 并核对 3008 健康，再启动 `fabric-readonly`，核对 3009 健康和只读标志。保存 PM2 进程表，配置系统自启，检查 `systemctl is-enabled pm2-root.service`、`systemctl is-active pm2-root.service` 和 daemon 的 cgroup。新机开放流量前验证 systemd 接管及恢复进程。检查公网 HTTPS、应用资源、真实 COS 缩略图及原图、相机页和权限头，再以已有发布证据运行 `npm run release -- baseline --evidence <release-result.json>`。基线要求已验证的应用、启动文件、Nginx 站点与数据库标识匹配。

## 发布工具固定流程

先运行 `npm run release -- plan` 了解阶段；本地离线工具验证为 `npm run test:release`。业务源码修改后，受控查看并批准源码集合的工具是 `node scripts/release/source-automation.mjs inspect` / `accept <精确文件>`，不能自动批准整个工作区。只有得到当前用户授权、目标数据库/服务器身份明确且备份可恢复，才能按冻结制品和发布计划执行发布。未知远端阶段结果只用原版本 `status` 核对，不自动重复重部署/迁移。

发布阶段必须验证：确切源SHA与生产旧版、目标MySQL身份/列约束、不可变制品、加密异地备份、必要的恢复演练、远端切换、`/api/health`/业务状态/鉴权、公网可信TLS及失败回滚。HTTP 200 或PM2在线不能单独视为成功。实际结果以 `artifacts/releases/<ID>/release-result.json` 等可验证原始证据为准。

发布前浏览器范围由[统一发布工具的自动验证规则](统一发布工具.md#自动浏览器验证范围)决定：已登记局部页面执行页面用例与公共冒烟，其他运行代码/迁移执行完整回归；`plan` 可只读查看选择，`--full-ui` 强制完整。不能以“改动很小”为理由手动省略验证、备份或线上核验。

正式发布按 `plan` → `prepare` → `preflight <ID>` → `deploy <ID>` → `verify <ID>` 执行，也可用 `run` 一次贯穿。登记迁移时先完成同一备份的隔离恢复演练，使用 `progress <ID>` 跟进，失败时用 `status <ID>` 核实阶段结果。发布验收后提交发布指针、推送、执行 `workspace:verify`，最后按 `prune` 的结果清理超量备份。

常规发布制品覆盖主应用首页、前端资源和 `dist/server.cjs`。Node 依赖、`dist/recovery.cjs`、相机静态制品及主机配置单独核验和更新。改变其中一项时，应在发布前审查其对应制品、依赖或配置摘要，并安排相应验证。

- **应用回退。** 对仍保留且当前版本匹配的制品执行 `npm run release -- rollback <ID>`，核对原首页、后端和公网健康。程序回退保留生产 MySQL 业务写入。数据库灾难恢复先在隔离库验证备份和 schema，再确认生产恢复窗口。
- **只读与依赖更新。** 单独核对 `dist/recovery.cjs` 与 Git 构建产物，启动后验证 3009 的回环健康、只读标志及写入限制。Node 依赖变更时按新锁文件在 Linux 准备并验证运行依赖，保留应用和依赖的一致快照。
- **相机更新。** `npm run build:camera` 后冻结 `dist-camera/`，校验制品和每个资源。复制到 `/opt/fabric/camera/<版本>`，以相对链接原子切换 `current`。从公网验证首页、JS、CSS 和权限头，再做客户选样手机扫码回归。失败时将 `current` 指回上一已验证版本。
- **主机配置更新。** 核对仓库模板和在线配置，保留配置备份。Nginx 先执行 `nginx -t` 再 reload。证书续签 dry-run 可以核对 ACME 和 reload 钩子。PM2 自启配置或 Node 版本变更后安排一次 systemd 接管及恢复验证。

涉及界面变更时，服务器和公网版本校验通过后按[生产 UI 只读检查](统一发布工具.md#online-ui-check)使用 Ego 浏览器检查改动入口，并登记实际结果。

## 数据与环境保护

客户/图片/导入源文件、`uploads/`、`template/`、`.env`、`.local/`、发布制品和旧生产备份绝不随知识库清理删除。MySQL主路径、图片COS、跨库FK/事务和真实浏览器/微信测试分别检查。图片资产迁移/回收详见[图片资产运维](image-asset-operations.md)。

最新系统状态参见[项目现状](../project/项目现状.md)，CI与上线审批参见[远端构建和发布Gate](fabric-v2-remote-build-and-deploy-gates.md)。

## 首次 V2 迁移留下的恢复约束

切流前必须冻结新备份、独立恢复并核验加密离机副本；停掉旧应用进程树及不识别 V2 图片引用的旧 worker。V2 已产生新写入后只切同版本 V2 只读恢复入口，不恢复旧可写 API，也不以旧 SQL 覆盖新数据。结构改变后的原值保护按原列逐值比较，不能跨结构只比较整表 CHECKSUM。旧启动自检曾产生订单汇总副作用，恢复旧进程前必须明确其写入行为。

历史生产、恢复库、回环性能、公网、浏览器与纸打/手机测试分别记录，不能互相替代；禁止向生产复制演练账号、客户、图片映射或性能夹具。10-19 具体包、备份、密钥恢复与审核原件在[恢复说明](../maintenance/文档整合与恢复.md#恢复位置)中成套定位；密钥及明文配置不入文档。未知执行结果或工具拦截先核状态，不换工具继续同一被拒动作。

## 交付检查与证据边界

单独的一期交付说明已合并到本节；唯一状态见项目现状，阶段源码入口见模块README，不维护第二份进度表。

`node scripts/check-fabric-v2-phase1-delivery.mjs --status` 只读核对正式入口的AST装配，不启动服务或连接数据库，不默认读取历史证据。未提供本次证据时八项验收可为pending、readyForReview:false，不能据此推断已经发布的应用未上线。

外部验收范围由检查器的 `PHASE1_EVIDENCE_GATES` 定义：目标MySQL迁移、备份恢复、角色/owner及旧接口、三库/COS、正式UI及用户接受、xlsx事务、三单据/历史输出、全链路安全/性能与回退。按本次变更和约定范围补证据，不因小修重复全部业务测试；本机/恢复库/公网/微信真机及纸质输出分别判定。

显式 `--evidence docs/operations/<本次证明>.json` 才加载 `fabric-v2-phase1-evidence-v1`。passed项须有reviewedBy、受约束Markdown proof路径和SHA-256 proofSha256；磁盘重读后拒绝缺失、空审核人、摘要失配、路径越界、符号链接及过大文件。历史签收按[恢复说明](../maintenance/文档整合与恢复.md#恢复位置)恢复原包，不改摘要冒充重新签收或新版本验收。

readyForReview:true仅表示指定资料齐备可评审，releaseAuthorized恒为false；发布/真实DB写入/切流/COS变更/旧库清退仍须各自明确授权，不由检查器授予或撤销。源码存在、HTTP通过、用户视觉接受和生产数据验收不能互相代替。
