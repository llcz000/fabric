# Fabric 统一发布工具

## Git 源码与收尾

准备发布前，先审查并提交源码，推送当前分支，执行 `npm run workspace:verify`。发布器在耗时构建前核对工作区干净及实际远端分支与 HEAD 一致，制品冻结前再次核对。制品的 `sourceGit` 保存提交号和远端核验，部署前要求当前工作区仍对应同一提交；缺少来源的新部署必须重新准备。部署成功后回执的 `gitCloseout` 初始为 pending。将更新的发布指针及项目现状通过 `workspace:commit` 提交推送后，执行 `workspace:verify`，核对发布源码的祖先关系及后续仅为这两类记录改动，回执变为 verified。旧发布回执保留原有来源信息，标记 legacy-unbound，不追认过去未记录的提交绑定。

> 2026-10-24 目录整理：本文部分历史路径对应的临时文件、已退役源码副本或旧发布证据已完整迁至仓库外；原路径作为历史定位保留，按[文档整合与恢复](../maintenance/文档整合与恢复.md)中的范围和逐文件 SHA256 查找原件。未完成的业务 Gate 仍按当前进度保留。

本工具承接已确认的固定流程：变更/源身份检查、一次构建和制品冻结、线上预检、一致性备份及加密离机、必要的恢复演练、迁移、原子安装、验证、失败代码回退。沿用现有 Node＋SSH＋Python，不增加服务或依赖。只检查发布涉及的内容，不默认跑全量测试，不在工具收尾修复历史文档。

固定入口为 `npm run release -- <command>`。配置只维护环境目标，旧版摘要从已核验的发布基线读取；日期和归档摘要由工具生成。详细日志写入每个制品目录，终端只显示阶段、结果和耗时。

普通发布和迁移发布共用同一执行器。迁移必须在代码登记、绑定计划摘要，并通过同一备份的隔离恢复和重复迁移验证。仅回退程序，不将历史SQL覆盖到生产。未知执行结果停止自动重试，通过status核对后恢复。

## 源码批准与 UI 专项

先执行 `node scripts/ui-workflow-gate.mjs inspect`：若是 `source-refresh-required`，按明确需求SHA和精确源码路径完成下面的登记，再依据最新 `expectedUiFiles` 创建本轮评审。不要修改历史报告的文件范围凑数；若UI已随上一版本发布且实际源码/候选/发布清单一致，返回无需新UI评审。`ui:verify` 对清单未登记的新UI、变更及删除均先行拒绝，避免通用“范围不匹配”掩盖清单过期。

- 取消人工逐条编辑 `source-manifest.json`：运行 `node scripts/release/source-automation.mjs inspect` 查看实际改动，再在人工确认改动文件后运行 `node scripts/release/source-automation.mjs accept <文件1> <文件2>`；只接受与实际变动集合**完全一致**的路径，任何额外改动、需求漂移、文件链接或错误工作区均拒绝，绝不自动批准全部工作区变更。 已核对的 `tsconfig.json` 可通过同一精确路径集合登记；这不开放任意根目录配置文件，也不改变源码完整性检查。
- 已明确批准的需求修订单独使用 `node scripts/release/source-automation.mjs accept-requirements <需求路径> <审阅后的SHA256> <AC路径> <审阅后的SHA256>`，仅接纳唯一需求及AC两文件的精确摘要，不能夹带源码；然后按原流程 inspect/accept 精确源码集合。
- 联系人稳定关联首次发布须登记 `--migrations sample-contact-identity`，只新增 customer_sample_sessions.contact_id 可空字段，保留既有姓名。
- 本单联系人（AC-163/164）首次发布须登记 `--migrations sample-contact`。迁移仅新增 customer_sample_sessions.contact_name 可空列，启动只读验证；隔离库恢复后验证字段和幂等，旧单不回填。
- 选样导出人工核对（AC-176）依赖 `customer_sample_sessions.card_review` 可空JSON列。相关服务/Schema变更的发布准备必须显式选择 `--migrations sample-card-review`，先一致性备份和隔离恢复演练，再执行登记迁移；只读启动校验拒绝缺列，不自动DDL。远端字段保护只允许该迁移新增精确的可空JSON列，不允许任何既有字段变化或额外新增列；登记迁移时必须同步此保护与回归测试。既有选样/来源不回填、不删除，首次导出按实际差异人工确认；用户暂停发布期间不执行生产迁移。
- 产品自动色卡首次发布必须显式选择 `--migrations product-auto-cards`，先做一致性备份和隔离恢复演练。`scripts/release/migrations.ts inventory DATABASE UUID - product-auto-cards` 只读盘点；补卡不改产品/图片、不复活旧码。发布器在新后端重启健康后、切换首页前再补齐一次，防旧服务切换窗口漏卡。迁移登记不会授予部署或真实库写入权限。
- 发布成功并验证线上制品之后，`cli.mjs` 自动同步 `docs/project/fabric-v2-active-workspace.json` 的 `currentRelease`。对发布前使用旧发布器而留下的状态差异，可在确认远端版本后执行 `node scripts/release/source-automation.mjs sync-pointer <已验证的发布ID>`；要求 release-result 与私有已验证基线完全一致。不把失败部署误写为上线完成。
- 面料主数据字段/Excel/DB 约束相关代码有改动时，发布准备阶段自动执行面料专项测试，防止预览与数据库约束不一致。
- 普通 `prepare/run` 按完整清单差异自动选择浏览器验证。精确范围、必测用例及完整回归条件统一见[自动浏览器验证范围](#自动浏览器验证范围)。`--full-ui` 可强制完整回归，旧 `--quick-ui` 仅断言命中已登记范围。
- `ui-quality-gate record` 自动保存候选专属且不可覆盖的截图快照；`ui:seal` 只在现有评审、浏览器和工程证据全部通过后封存UI工作流截图，不改变用户签收与发布状态。普通prepare先seal、再跑浏览器，构建前复核证据；通用截图重写不能破坏冻结快照，快照篡改仍拒绝。
- 发布工具自身新增保护性单元测试，验证源码改动白名单、指针只在发布成功后更新、快速 UI 的精确适用范围；生产备份、异地读回、需要时的恢复演练、原子部署、线上核验和失败保护全部保留。

## 自动浏览器验证范围

范围比较使用上一已核验发布的 `package/source-manifest.json` 与当前已审核候选清单，先通过实际源码新鲜度检查，不能按脏 Git 工作树或手填文件名缩小范围。文档改动不作为运行代码影响；需求、源码和 UI 规范的原有摘要门禁仍然保留。

| 已登记范围 | 页面检查 | 额外保留 |
|---|---|---|
| 模特图库 `ModelGalleryV2.tsx` 及其专属测试/预览夹具 | `model-gallery.spec.ts`，覆盖完整图片、3:4排列、导入toast、编辑/删除取消和换装下载回归 | 公共列设置键盘/焦点及产品/色卡桌面手机操作列冒烟 |
| 面料列表 `FabricLibraryV2.tsx` 及其专属测试/预览夹具 | `internal-fabric-design.spec.ts`、`internal-fabric-weight-unit.spec.ts`、`related-products.spec.ts` | 同一组公共冒烟、`FabricLibraryV2.test.ts`、构建后原有面料列宽几何检查 |
| 客户档案和客户选样 `customer-selection`，精确文件以 `scripts/release/browser-validation.mjs` 为准 | `customer-delete-address.spec.ts`、`sample-directory.spec.ts`、`scan-selection.spec.ts`、`sample-card-review.spec.ts` | 公共冒烟、客户服务及 HTTP、选样读取/列表/扫码授权、客户关联单据和前端请求回归 |

只有上述范围中的精确登记路径可缩小范围，多个范围取用例并集且去重。未登记的后端和共享代码、发布器、依赖/配置、公共冒烟自身、未知路径均执行完整回归。新增/删除代码、必测文件缺失、迁移及 `--full-ui` 同样触发完整回归。新增登记须同时补充所有权、关联用例和回退边界测试。

浏览器调用固定为仓库内安装的 Playwright CLI、正式 `playwright.ui.config.ts` 和单 worker。逐项进度写入 `ui-browser-progress.log`，完整 JSON 结果单独写入 `ui-browser-tests.log`。命令失败、报告异常、零通过、缺少任何选定 spec 的通过结果或出现失败/不稳定用例均阻断。公共冒烟和页面用例共用一次预览构建。

`prepare` 保存 `browser-validation-plan.json`（模式、原因、基线ID、候选SHA、精确变更、规则版本和用例）、`browser-validation-result.json`（实际命令、通过/跳过数量和通过文件）及执行日志；计划和结果一起进入冻结包并校验摘要，manifest、发布回执和 `report` 记录同一选择。模式为 `scoped`、`full`、`none`；已核验制品复用单列 `reused`，不冒充本轮测试。`--full-ui` 不与 `--quick-ui` 或 `--from-release` 混用，也不能修改已有发布ID的冻结计划。

定向发布从统一发布器 `run` 启动到线上版本验证的目标为 5 分钟。进度输出给出 `wallElapsedMs`、`targetMs` 和 `overTarget`。源身份、视觉/交互证据、HTTP 合同、正式构建、备份/加密离机、必要恢复演练、原子部署、线上验证和失败回退仍按原门禁执行。分开记录本地回放耗时和真实生产端到端耗时。

首次把这批发布器改造纳入正式发布基线时，工具文件仍相对旧基线有变，必须完整回归一次；该发布核验并同步基线后，后续精确命中登记范围的局部改动才进入定向流程。不得手改旧发布清单或排除工具差异来提前获得局部判定。

## 使用

在唯一项目根目录 `D:/fabric` 执行。

```powershell
npm run release -- plan
npm run test:release
# 首次安装或恢复本地发布状态时，以已发布证据核对现场后初始化；不盲目接纳线上漂移。
npm run release -- baseline --evidence artifacts/releases/RELEASE_ID/release-result.json
# 普通发布，一次构建后贯穿所有必要步骤。
npm run release -- run
# 发布运行中另开终端，可查看最近一次或指定 ID 的阶段和当前测试项。
npm run release -- progress
npm run release -- progress RELEASE_ID
# 本地强制完整浏览器回归并构建，不发布。
npm run release -- prepare --full-ui
# 先准备再查看/演练，不发布；ID由prepare输出。
npm run release -- prepare --migrations card-share,light-customers
# 工具演练复用当前已上线制品；要求当前server/src与发布源一致，不重新构建应用。
npm run release -- prepare --from-release artifacts/releases/RELEASE_ID/release-result.json --migrations card-share,light-customers
npm run release -- preflight RELEASE_ID
npm run release -- rehearse RELEASE_ID
# 真正执行发布：复用该ID，不再次构建。
npm run release -- deploy RELEASE_ID
npm run release -- verify RELEASE_ID
npm run release -- status RELEASE_ID
# 本地耗时报告，不连接生产。
npm run release -- report RELEASE_ID
npm run release -- resume RELEASE_ID
npm run release -- rollback RELEASE_ID
```

`prepare` 和 `plan` 不访问生产；`preflight` 上传固定制品、核对线上版本/物理数据库/PM2/恢复服务并执行登录读取，不切换程序；`rehearse` 在此基础上备份、加密离机校验、恢复到唯一隔离库并检查登记迁移，最后仅删除本次新建的演练库。`run`/`deploy` 会迁移并切换生产，必须处于用户已授权发布的任务中使用。`verify` 仅验证已经安装的版本，`status` 仅读取远端状态，`report` 仅读取本地耗时证据，三者不会隐式发布。

`progress` 只读本机准备和各阶段回执，在制品冻结前也可使用。浏览器检查显示当前用例序号、总数及名称。部署阶段显示当前动作，结束后显示已验证或失败状态。同机并行操作时指定发布 ID，避免读到另一轮准备。

已成功阶段不会重复执行。失败时保留日志，通过 `status` 查看服务器回执；`resume` 明确恢复，可安全重试的只读/传输步骤复用原制品。服务器标记为“正在执行”且结果未知的备份、迁移安装或回退不会盲目重试，应先检查证据并完成受版本保护的回退或人工收敛。已回退制品不能再次发布，需要新ID。

## 配置和证据

- 环境配置：`scripts/release/production.json`，只保存固定目标、进程和数据库身份；无密码或密钥。
- SSH沿用 `.local/server/_config/ssh.local.json` 和既有主机密钥校验。发布基线及离机备份口令保存在其旁的私有 `release-state` 目录。
- 每个制品：`artifacts/releases/RELEASE_ID`，保存 `run.json`、固定manifest/归档、构建/远端日志、加密备份、离机校验、阶段耗时；成功发布产生标准 `release-result.json` 并更新已验证基线。
- 远端也保存各阶段回执；制品和执行器均按SHA固定，后续工具更新不影响使用旧制品内的执行器回退。
- 新迁移在 `scripts/release/migrations.ts` 登记，更新 `core.mjs` 的允许ID并补充相关测试。可用ID统一由 `core.mjs` 的 `migrationIds` 提供，`plan` 输出同一列表；具体计划与所需演练仍由各迁移实现限定；不允许从JSON注入任意SQL或shell。需要改变既有表结构的迁移应补充相应保护和专用演练，不能绕过现有旧列保护。
- 默认执行源身份、自动浏览器范围选择、完整HTTP合同和一次正式构建。局部浏览器检查仍重新执行，不复用开发阶段旧通过日志；`test:ui:ux` 保留为手动完整浏览器入口。`test:release` 验证发布器、范围选择/执行、源码、UI证据、远端故障和HTTP合同，不跑整库业务单测。`fullSuiteRun:false` 指未跑整库业务单测；浏览器是否完整执行由 `browserFullSuiteRun` 和 `uiBrowserScope` 单独记录。HTTP验证不代表浏览器或微信人工签收。

## 维护边界

今后正常发布使用此入口；既有日期脚本保留为历史证据，不作为默认发布入口，不再复制生成下一套日期脚本。只在变更影响发布器时运行 `test:release`；业务变更不应反复修改发布器。源码、环境或制品漂移立即停止，先查明确切差异。

`--from-release` 只接纳与本地已核验线上基线完全一致的已发布归档，并核对归档、真实首页/后端、浏览器文件和源清单摘要。当前server/src代码还要与该源清单一致，才能检查复用制品的HTTP合同；不会把未审阅的新代码伪装成已验证制品。正常的新业务发布仍须走源码门禁和构建。

## HTTP 合同、失败恢复与验证边界

`prepare` 在应用构建前启动完整正式 HTTP 装配，以固定测试身份检查退出路由和匿名拒绝，不读写真实数据库。`http-contract.json` 随制品摘要冻结，供本地与远端使用；旧路由误返回 404 而非合同要求的 410，应在上传前失败。HTTP 合同检查不代替业务、浏览器或微信验收。

远端失败即使以非零退出，也应将自动回退回执保存到本地；断线后先查询状态，确认回退的 ID 不得再次发布。`report` 仅统计真实非重叠阶段，缺失的历史耗时不补造，不能把复用准备或排除等待后的累计值当作完整开发提速。

历史 10-20/21 工具测试、演练、失败回退和耗时流水已存入[恢复包](../maintenance/文档整合与恢复.md)，保留其原始证据路径与环境边界。原记录中“错误回执传输与合同保护待下一次真实远端闭环”的事项没有在本次清理重验；遇到相关发布须核对真实回执再关闭。当前生产状态以[项目现状](../project/项目现状.md)和对应冻结制品为准，不采用手册中的历史版本号。
