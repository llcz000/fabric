# Fabric UI 产品定位与迭代原则（2026-10-21）

**已明确的产品边界**：Fabric 系统（花型、面料、产品、色卡、客户、客户选样、三类单据、设置等）均为公司内部操作界面。**仅通过色卡分享链接打开的资料展示页面面向客户**。内部员工分享动作仍属于内部操作，不等于客户展示页面。

## 1. 内部工作台：效率第一
- 最短完成任务路径：**清晰、稳定、少跳转、少重复输入**；高频操作优先于装饰视觉，避免顶部大 Hero、营销文案、无用统计面板、大图画廊挤占首屏。
- 默认布局：适度紧凑的标题与主操作 → 搜索筛选 → 可比较的列表/表格 → 分页/状态。花型缩略图在业务需要时有，尺寸仅满足识别；点击后原图放大，不强制所有列表改卡片。
- 操作：核心操作常驻可见且易找；同类页面按钮、筛选、编辑和反馈方式一致。简化表单、可恢复草稿和取消，避免多层弹窗。数据正确性和权限边界始终优先。
- 视觉：整洁、现代、清楚，有品质但**不能增加操作成本**；文本字号可读、间距适中，色彩不制造无意义的层级。无强制 A/B 或强制设计工具流程。
- 目标终端：以实际内部桌面工作流为主，移动端按扫码/选样等真实操作场景重点优化，不为营销美感牺牲桌面效率。

## 2. 客户分享页：展示清晰优先
- 仅**色卡公开分享链接最终打开的页面**采用适合客户浏览的图片优先设计：花型、配色、面料规格、面料图、细节图、效果图成组，易翻看、易辨识。
- **以微信内置浏览器手机竖屏为首要场景**：首屏快速呈现花型/色卡身份与面料规格、配色直接跳转、图片等比和点击放大、可视高度与安全区、至少 44px 触控区域。首张优先，其余懒加载；不要求微信 JS-SDK 或自定义分享卡片，不能用浏览器模拟代替 iOS/Android 微信实机验收。
- 此页面不出现内部管理入口、内部角色/状态、内部敏感字段、编辑与删除等操作；真实公开分享依服务端白名单、授权和失效规则验证。
- 不把客户展示风格倒灌至内部系统。内部“分享预览/复制链接”的按钮和弹窗仍以操作效率为准。

## 3. 迭代速度及架构
- 优先**复用现有 React 业务组件、model、表格/表单/弹窗与语义 Token**；业务规则/数据和展示风格解耦，禁止为一次视觉实验平行重写全部内部业务逻辑。
- **最小必要修改**：已有风格和交互已验收的页面只做局部修改，不扩大成整页重设计。不同业务对象只共享真正一致的组件，不为了抽象而抽象。
- 工具按需：Stitch、Magic Patterns、Figma、v0 属于可选探索手段；简单字段/筛选/文案变更**不强制设计稿或双方案**。重大新页面或客户分享页视觉重设计可做小范围方案对比。
- 测试分层：小修做针对性检查；核心操作/公共组件修改增加受影响的 Playwright 主路径、取消/错误、焦点和屏幕布局；发布前再按统一发布门禁补足端到端和回归。**不能用全量慢测试拖住每轮小修，也不能因为赶进度放过高风险变更**。
- 文档维持一个事实源：现行业务来自最新需求，视觉边界在本文件，交互在 component-rules，验收在 ux-delivery-gate；旧 A/B 探索稿只是历史案例，不是强制界面模板。

## 验收次序
(1) 业务正确 / 不破坏既有流程 → (2) 高频操作速度与可发现性 → (3) 一致与可维护性 → (4) 可读的专业视觉 → (5) 有针对性的自动化证据。对客户分享页增加媒体呈现质量和移动端阅读体验验收。
