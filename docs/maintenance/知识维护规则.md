# 知识维护规则

> 文档定位：维护与模板｜主要读者：文档维护者、Agent。用途：清理追溯、恢复或写新记录时使用。

更新：2026-10-15。适用Fabric DMS应用项目文档；视频制作内容已移出，不再纳入本库当前导航。

1. docs/00-首页.md是唯一总入口；项目业务范围及既有需求在docs/project/项目需求总览.md维护，技术方案、模块划分、切片与所有权在docs/project/项目设计.md维护，项目状态在docs/project/项目现状.md维护。产品主数据V2的新增/替换细则只在docs/product-master/product-master-v2-requirements.md更新，模块阶段状态在其进度维护；领域README只作导航。不能把模块PRD称为完整项目需求，也不能因未提及就取消范围外的已有功能。
2. **需求只写做什么与验收判据，不写怎么实现、交给谁实现**；实现方案、数据结构、接口契约、任务切片一律进项目设计文档。设计结论须引用需求条目编号，需求变更时连带复核设计文档；两者冲突以需求为准并修订设计。
3. 文档均明确类型、主要读者、用途：需求供业务决策，当前进度供负责人判断，过程供当前开发/验收，经验供同类问题复用；手册供日常设计/开发/运维，维护记录仅在追溯或清理时看。所有保留文件在docs/文档分类与检索.md按关键词登记。现状在project/，通用开发规则在development/，运维在operations/；复盘统一在retrospectives/development/。未完成的独有设计/计划仍在superpowers/specs及plans，不因日期旧而删除。
4. 一件事只保留一份当前说明。更新原文，不在README/首页/进度重复追加整轮日志或相互冲突的版本摘要；同根因零散复盘合并后保留分模块证据与未验项。
   项目需求先说明业务场景和流程，再列支撑场景的功能、性能、可靠性要求；按功能直达编号条目。角色、登录与授权集中一节；实现现状维护在进度，待确认项集中列出。不在需求正文堆阅读指南、分类说明或重复解释；图示仅在有助理解且易维护时使用。
5. 删除前提取独有批准约束，确认替代位置并更新引用；先列文件白名单，校验仓库外可恢复备份，逐项核验路径。文件级SHA256、动作及替代关系登记到维护清单，不在项目内另存完整旧知识库。
6. 当前事实写核对日期、源码/环境；旧测试数量、交付哈希或线上结果只对应原日期。未重新执行/核验就明确说明，不将计划或本机替身测试当作实库/部署完成。
6. 新文档进入相关索引；移动/合并同步修复Markdown、技能/脚本路径和artifacts交付引用。历史清单中的原始路径可保留作追溯，不作为当前入口。
7. 运行/客户数据、.env与本机连接配置、uploads/template、原素材、成片、用户设计稿、验收证据、开发恢复基线及有独有工作的worktree不属于旧知识。无引用不等于可删，不借文档清理删除这些内容。
8. 不保存密钥、token或客户敏感数据；通用记录只保留脱敏事实。Obsidian工作区状态不提交。

## 任务完成后的强制归档 Gate

**触发时机：** 每个阶段/AC/缺陷在**本批验收结束、交付前**必须做一次历史文档分类审查；同主题后续完成验收时重新审查。判断结果只能是`保留`（仍有未验收Gate或独有依据）、`归档候选`（满足下面条件）、`不适用`（本批无可替代历史文件），记录在当前专题交付/复盘中。检查归档机会是强制的，**自动删除不是强制也不允许跳过安全审查**。

**归档资格（择一成立）：**

1. `fully_accepted`：对应任务的业务验收及其要求的API/真实MySQL/UI/部署Gate全部在约定范围内关闭，且存在明确的验收结论和证据；仅有单测通过、本机演示、Agent自报完成，不够。
2. `superseded`：即使整个业务包仍有开放Gate，待退出的旧过程记录已被新专题**完全替代**，经人工逐项确认：独有批准决定/安全边界/失败原因/验收环境与证据链接已转移；尚未完成的Gate仍在[当前进度](../product-master/product-master-v2-progress.md)和现行专题中可定位。不得因旧文档无人引用或版本旧就推定满足。

**绝不自动移出的内容：** 唯一现行需求、批准决定、进度、仍有独有设计约束的规划与架构、未关闭迁移/回滚/权限/真实环境Gate的唯一证据、当前设计稿/用户改稿、测试截图/数据库或客户数据/媒体/运行配置、Git源码及恢复基线。归档仅针对有证明的*重复或过时的过程/复盘Markdown*，不对整个目录做批量清除。

**每次归档严格按顺序操作（缺一步即停止）：**

1. **范围与审查**：限定具体历史Markdown白名单，逐篇核对当前需求、完成/替代证据、独有约束、尚存Gate；同一旧记录涉及多个任务则按**最晚仍需的Gate**判断。将结论、替代路径和人工审核记入任务复盘或维护记录。
2. **提炼和修复链接**：将独有事实、操作警示和开放Gate写入唯一合适的现行专题/复盘/进度，调整所有当前README、目录、相对链接、技能/脚本引用；不要在多个README复制一套业务规则。
3. **可恢复备份**：原件逐文件保存到项目外`D:\\fabric-knowledge-backups`中的本批独立目录；产生相对路径、字节数、SHA256清单，并对备份**重新读取逐文件核验**。不能覆盖旧备份，也不能把副本留在会被tsc/检索扫描的项目目录里。
4. **机器只读预检**：对每个候选准备`fabric-v2-doc-archive-plan-v1`复核清单，执行`node scripts/check-fabric-v2-doc-archive.mjs <review-plan.json>`；核验原件/备份哈希、当前证据、替代文件、独有事实/开放Gate去向及仍存的Markdown入口引用。FAIL或缺人工语义审查必须停止，**此命令永不删除文件**。
5. **受控移出和验收**：仅对本批已授权、预检PASS的白名单逐个移出日常`docs/`；更新分类索引、维护映射、复盘和进度，再运行`node scripts/check-fabric-v2-doc-navigation.mjs`、技能/P0静态Gate及`git diff --check`。任何索引断链、遗漏证据或新增风险必须恢复本批涉及文件，不影响其他用户改动。
6. **回退**：从仓库外清单对应文件选择性恢复，先核SHA256和目标当前版本，必要时先创建不覆盖的新文件供比较；禁止整包覆盖/重置仓库或恢复过时业务规则为现行要求。

**复核清单格式与字段**（推荐保存在本批临时目录，不放进现行业务索引）：

| JSON字段 | 要求 |
|---|---|
| `format` / `entries` | 固定 `fabric-v2-doc-archive-plan-v1`；`entries`为非空逐文件白名单 |
| `source` / `replacement` | `docs/`内旧过程文档和已存在的现行替代文档相对路径；不能指向同一文件或归档受保护需求/决定/当前进度 |
| `reason` | 仅 `fully_accepted`（全范围验收，无开放Gate）或 `superseded`（新专题已承接仍开放的Gate） |
| `evidence` / `evidence_phrase` | 可打开的当期任务证据文档及其中可逐字检索的原文段；语义是否充分仍由审核者判断 |
| `unique_information_reviewed` / `open_gates_reviewed` | 必须在完成逐项人工复核后显式为 `true`；布尔值不能替代审查 |
| `retained_facts` | 至少一条 `{ "file": "docs/...", "phrase": "已迁入的实际原文" }`，检查接收文档中是否确实可找到 |
| `pending_gates` | `fully_accepted`时必须为`[]`并附 `acceptance_confirmed: true`；`superseded`时逐条列 `{ "file", "phrase" }`，无开放Gate也明确填`[]` |
| `archive_copy` / `sha256` | 项目外已实际存在的备份文件绝对路径，以及原件与备份都一致的64位小写SHA256 |

脚本只打印PASS/FAIL及候选路径；没有移出/删除动作。复核计划中的 `reason`、转移事实和验收判断不可由Agent根据“旧日期”“无引用”自动杜撰。旧文档若已删除，只能先从仓库外选择性恢复到**不覆盖现有文件**的审查环境，不能为了通过预检重造内容。

机器检查器验证的是**可追溯的结构化证据**，无法判断人类业务验收是否真实充分、每条独有约束是否完全提炼；最终人工语义复核、任务授权及真实环境Gate依然独立。`fully_accepted`清单不得带开放Gate，`superseded`必须把开放Gate指向在库现行文件。项目级规则详见`AGENTS.md`；Agent交接和复盘模板应记录分类结果。

## 提炼与新建门槛

- 日常固定为一份项目需求总览、一份项目设计开发验收进度；缺失的既有需求先恢复并标明确认缺口，未补齐不称“完整需求”。模块细则按项目总览链接维护，不复制全文；阶段只保留按主题的技术说明。除新增跨任务可复用的根因外，不再同时创建“交付报告＋复盘”。测试流水、重试日志及完整工具输出留在证据或仓库外备份，不进入日常正文。
- 开放Gate本身不要求整篇过程原文永久保留。独有约束、验收环境/证据与开放事项转入现行专题和唯一进度后，按`superseded`走本页归档检查；不必等全部项目上线，也不得把文档归档当成业务验收。
- 先判断新增信息属于业务要求、实现状态、单次证据还是可复用规则，更新对应唯一位置；不要把一段结论同时复制到README/进度/过程/复盘。
- 新文件必须回答“谁会因什么问题打开它”，相同主题已有位置就更新；临时试错和每轮通过数量留在该主题证据，不能直接成为新规范。
- 已批准但未完成的独有约束保留；过程原文先仓库外哈希备份，再提炼代码定位、关键验收与开放风险，统一修复引用，不能仅因日期旧删除。
- 日常入口最多展示问题/专题，完整文件表集中维护在分类检索；历史原件/合并映射进机读清单，不重新铺满首页。

## 复盘回流

问题与触发 → 根因/修复 → 实际环境和验证 → 未解决Gate → 适用经验回流开发或运维。模板见[开发复盘模板](../Templates/开发复盘模板.md)。同主题已有记录时直接更新，独有证据保留在一个主记录中；不复制另一份全文。

## 文档验收

检查全库相对链接、索引可达性、被删路径的当前引用、文件白名单、备份哈希/CRC与Git差异；源码/脚本/依赖须与本轮基线一致。新增任务导航或移动入口时运行`node scripts/check-fabric-v2-doc-navigation.mjs`，验证P0～P7/B1～B3源码路径和主要导航，避免“链接存在但版本过期”。纯文档整理只跑文档静态Gate，不启动或连接服务、不跑会写库的脚本。发现旧Gate与现行需求不一致时如实标明，不为通过检查改业务规则。
