# 知识维护规则

> 维护准则。需求写业务，设计写实现，状态写已完成/未验，手册写可重复操作；不在本文件积累每轮清理流水。

## 唯一位置与准入

| 信息 | 唯一维护位置 |
|---|---|
| 全项目业务与批准范围 | docs/project/项目需求总览.md |
| 产品主数据及关联业务的 AC 验收场景（不定义业务规则） | docs/product-master/product-master-v2-requirements.md |
| 实现设计、接口、安全及迁移约束 | docs/project/项目设计.md、数据与API.md |
| 当前状态与开放Gate | docs/project/项目现状.md；模块进度只作定位，不复制状态 |
| 可重复开发/UI/运维操作 | 对应现行手册；版本和精确命令以源码/配置为准 |
| 运行证据、旧审计、测试日志、清理清单 | 现有制品证据或同批仓库外备份，不能新建日期报告堆积 |

docs/00-首页.md 是唯一总入口，分类检索只作导航。需求只写做什么和验收判据，技术方案按需求编号落到设计中；冲突以最新明确批准要求为准。

`docs/project/fabric-v2-active-workspace.json` 是机器读取的工作区/发布指针，不是状态叙述入口：只保留被工具消费的结构化字段和可验证回执引用；发布事实与待验边界写入 `docs/project/项目现状.md` 或正式发布回执，不在 JSON 中追加自由文本说明。

新增文档默认禁止；确需新增时必须得到业务负责人明确批准，同时满足：有独立长期读者和问题、现有文档无法合理容纳、有明确权威来源及退出条件，并同步登记脚本 Registry。否则更新已有专题。禁止为同一轮工作分别生成计划、交付、复盘和摘要；只有出现可跨任务复用的新根因时才更新已有复盘，确需新主题时用模板并登记索引。用户要求不新建过程文件时优先遵守。

## 保留、合并与退出标准

- **保留**：现行需求/规则、仍有效的独有批准证据、真实运行或测试入口及其必要配置、尚未转移的独有设计和开放Gate。必须能说明谁会因什么问题打开它。
- **合并**：同一规则或技术约束多处重复，只保留一个正文；其他入口改链接。代码可直接查询的列数、默认值、依赖版本、每轮测试数字不在多份规范抄写。
- **归档候选**：重复、被新专题完整替代的过程记录，先转移有效约束/证据环境及未验事项，再退出日常目录。仅加“历史参考”不是完成目录收敛。
- **不适用**：本任务没有可替代历史文件，不为交付格式创建空报告。

日期旧、无引用、单测通过或 Git 干净均不能单独证明可删。引用存在也不是永久保留理由：先判定该引用是否仍必要，再修复调用方或入口。原始批准证据和用户改稿不能擅自改写签收含义。


## 2026-10-24 根因记忆：为什么曾经反复出现重复文档

反复失败不是执行人员忘记删除文件，而是原规范**只有原则、没有机器约束**：总览和V2细则都在写业务要求、版本标记继续让旧长稿成为入口；改业务后没有ID关联的逆向影响分析，旧UI/验收/Skill/脚本继续携带已废止规则；阶段性计划/结果文档虽有归档规范，但新增时缺少准入Gate；原导航检查主要验证“文件与链接存在”，并不验证唯一事实或业务语义。这四种机制缺陷必须同时防止复发，不能只做周期性打扫。此前清理64→39文件的经验说明“删掉旧文档”不等于“以后不会再产生垃圾”。

## 强制的唯一事实、知识图谱与变更协议

1. **唯一业务正文**：`docs/project/项目需求总览.md` 的表格需求ID（如 CUSTOMER-07 / LITE-01）是业务规则唯一可修改位置，修改旧规则应直接**改原ID条目**，不叠加“2026新决定覆盖旧条款”段落。不删除或重编号既有ID，废止则就地标明取消并移除生效要求，关联状态按项目现状核实。
2. **AC不立法**：`docs/product-master/product-master-v2-requirements.md` 只允许可测试的AC场景及指向唯一需求的链接，不能再复制业务正文。项目设计只写“如何实现”，项目现状只写“已做/待验”，UI/运维/开发手册只写各自的可复用操作，复盘只保留已有索引上的跨任务经验。相同业务决定不得在多个文件重述成规范。
   - **追踪强制列**：每一 AC 的 `对应需求ID` 必须直接列出真实有效的当前需求ID；多个用英文逗号分开，新增/修订时同步核对业务规则、正反测试和受影响代码。AC与需求的关系只维护在验收表，不在注册表或其它文档复制映射。无直接AC的需求应在知识图谱中保持可见（可能是后续库存、单据/统计或等待补测试），不得谎称全需求具备验证覆盖。
3. **改动前查影响**：`npm run knowledge:impact -- CUSTOMER-07` 或 `npm run knowledge:impact -- AC-105` 查看需求↔验收用例→受影响业务域→相关文档/实现/测试候选；只编辑单个文件时用其项目相对路径查询；改动后运行 `npm run knowledge:changed` 输出Git工作区变化的候选影响，再核对真实代码调用、数据库、前端、权限、报表、数据迁移及相关测试。发现影响域缺失时先补 `scripts/fabric-knowledge-registry.json` 中的关系，不得仅修改文字就宣布结束。
4. **交付时强制检查**：`npm run knowledge:check` 包括唯一权威/唯一ID/全需求域归属/文档准入/旧规范链接检查和反例测试。GitHub审查CI同样运行；跨域需求改动须说明影响域及实际专项验证，对不需要改的域作出明确“无需修改”判断，不得将域级候选误称为需求到函数的精确验证。机器只检查可编码的矛盾及关系；是否与真实代码/用户决策一致必须逐项人工评审。
5. **新文件默认禁止**：当前保留Markdown文件名在`scripts/fabric-knowledge-registry.json`中形成白名单；未经登记的新Markdown或过程JSON让门禁失败。即使登记，新按日期命名的计划、审计、评审、总结和结果文档仍被阻止。确需增加真正长期可用的文档时，必须事先说明唯一读者/用途/维护人/退出条件、由业务负责人明确批准、更新Registry及入口、验证没有现行文件能够承载；不用“临时先建后合并”绕过。
6. **一轮任务一处写入**：业务变化改唯一ID，技术变化改唯一设计/API说明，当前状态仅更新项目现状。测试日志、运行JSON、画布快照、发布回执保留原工具制品路径或仓库外备份，禁止扔进docs。图谱为按需查询生成（`npm run knowledge:map` / `node scripts/fabric-knowledge-graph.mjs map --mermaid` / `--json`），不得提交由这些命令生成的报告副本。
7. **知识完整性不等于全量重测**：影响分析帮助选择最小必要测试；没有明确关联的文件是待补证据，不自动认定已验。任何真实数据库、COS、生产部署、客户数据等仍按独立授权处理。

借鉴开源项目而不引入重平台：GitLab Docs 文档随代码走CI并检查内部/跨源码链接（https://docs.gitlab.com/development/documentation/testing/）；Backstage TechDocs采用docs-as-code，Software Catalog有dependsOn等关系（https://backstage.io/docs/features/techdocs/；https://github.com/backstage/backstage/blob/master/docs/features/software-catalog/well-known-relations.md）；Diátaxis区分教程、操作、参考、解释，避免类型混杂（https://diataxis.fr/）。Fabric只采纳“唯一源、稳定ID、元数据关系、双向影响、强制检查”这些轻量部分，不建设新的Obsidian手工画布、图数据库或按日期的研究报告。

## 任务完成后的强制归档 Gate

每项任务收尾在现有专题或当前状态记录相关历史资料的保留/归档候选/不适用；不为这个字段新建文档。资格仅两类：

1. `fully_accepted`：本任务约定的全部验收已通过，有实际范围与证据；未测不能算通过。
2. `superseded`：新专题已承接独有批准决定、安全约束、失败原因、证据环境和开放Gate。项目整体尚未验完不妨碍已替代过程原文退出；未验事项仍在唯一状态中可定位。

按顺序执行，缺一步停止：

1. 列精确文件白名单，逐篇语义审查及替代定位；检查代码/脚本/技能/当前需求的依赖，不能批量清目录。
2. 提炼独有约束与开放Gate到现有权威文件，同步修复所有当前入口、脚本和链接；不把旧任务ID、旧漏洞、旧测试数恢复为今天的待办。
3. 在仓库外 `D:/fabric-knowledge-backups` 的同批目录保存相对路径、字节数、SHA256及原件独立副本，重新读取逐文件验哈希；不覆盖旧备份。
4. **机器只读预检**：外部 `review-plan.json` 使用 `fabric-v2-doc-archive-plan-v1`，运行 `node scripts/check-fabric-v2-doc-archive.mjs <review-plan.json>`。FAIL不得移出；PASS也不是删除或部署授权。
5. 仅按已授权、已审查白名单移出；验证导航、技能/相关静态检查、精确源码差异和 `git diff --check`。出现断链或遗漏约束，恢复本批对应原件并修正，不重置其他人的工作。
6. 恢复时先核清单和文件哈希，在独立目录比较后选择性恢复；禁止整包覆盖较新源码/需求/配置。批次审查、哈希及移动回执留在同一仓库外清单；临时执行脚本用完删除。

预检清单逐项包含：`source`、`replacement`、`reason`、`evidence/evidence_phrase`、`unique_information_reviewed:true`、`open_gates_reviewed:true`、`retained_facts:[{file,phrase}]`、`pending_gates:[{file,phrase}]`、`archive_copy` 和64位小写 `sha256`。证据与短语必须真实存在；fully_accepted另需acceptance_confirmed:true且pending_gates为空。布尔值和机器检查不能替代人工语义审查。

## 源码、数据和临时输出

HTML、TS、JSON按实际用途判断：正式入口、测试夹具、构建/测试配置及依赖锁均可能是必需源码；不按扩展名删除。废弃入口退出时连同调用方和源码清单精确调整，保留其它源哈希，不自动接纳未知改动。

运行/客户数据、.env、.local、uploads/template、原始Excel/图片、成片、用户设计稿、当前和回退冻结制品及有独有工作的工作树受保护；不是文档垃圾。临时测试输出由创建方在进程退出后清理；发布证据按恢复依赖保留。普通开发默认单工作区、单Agent；不为整理目录创建新工作区。

同轮目录或行为改变必须连带核对现行规范、技能和检查器。链接可打开不等于内容正确；过时断言须用真实正例与负例修正，不能恢复已取消规则求绿。历史测试、模拟API、真实MySQL、浏览器、微信真机、人工视觉及正式发布分别记证据，未验不签收。文档不存密钥、令牌、连接秘密或客户敏感数据。

恢复总入口为[文档整合与恢复](文档整合与恢复.md)；此处只维护通用规则，不追加日期补丁或每轮通过数量。
